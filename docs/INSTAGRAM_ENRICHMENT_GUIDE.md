## 🚀 다음 세션 시작 가이드 (이것부터 읽을 것)

**현재 상태**: 아티스트 336/1,110 확보(774명 남음, 이 중 n≥2 출연 106명이 우선순위) /
DJ 73/155 확보(82명 남음, WebSearch로는 원천 불가 확인됨 — 아래 참고).

**시작 순서**:
1. `SELECT id, display_name FROM artists WHERE instagram IS NULL AND deleted_at IS NULL`로
   미확보 목록을 다시 뽑고, `club_event_performers` 출연 횟수로 정렬해 n≥2만 추린다.
2. **크로스매치부터 전수 스캔** — 미확보 목록과 기확보 목록을 이름으로 대조해서, 한글/영문
   표기가 각각 다른 행으로 존재하는데 한쪽만 채워진 경우를 찾는다(예: `Deepflow`는
   확보됐는데 `딥플로우`는 미확보). 검색 없이 핸들만 복사하면 되고, 지난 세션엔 이 방식
   으로만 28건을 풀었다. WebSearch보다 먼저 할 것.
3. 남은 것만 WebSearch로 검색. **검색어는 반드시 `{이름} 래퍼` 또는 `{이름} 디제이`만
   쓴다 — 클럽명·행사명을 절대 붙이지 말 것.** 클럽명을 붙이면 클럽 공식 계정이 상위로
   밀려 올라와 오히려 방해된다(실측 2회 반복 확인). 아래 "검색 실전 팁" 섹션 참고.
4. 확신 없는 이름은 저장하지 않고 넘긴다 — 미입력이 오연결보다 낫다는 원칙은 절대
   원칙이니 유지할 것.

**⚠️ 자꾸 스스로 멈추는 문제 — 반드시 읽을 것**:
지난 세션에서 사용자가 "왜 자꾸 멈추냐"고 지적했다. 원인은 두 가지가 섞여 있었는데
**대부분은 하드 제약이 아니라 에이전트 스스로의 판단**이었다:
- **진짜 하드 제약**: 세션당 WebSearch 호출이 약 200회로 제한된다. 이 한도에 닿으면
  검색 자체가 조용히 실패한다(결과가 텅 비어 보인다 — "못 찾았다"가 아니라 "검색이
  막혔다"는 뜻이니 저널/트랜스크립트를 열어 확인할 것, 위 "WebSearch 세션 예산 한계"
  섹션 참고).
- **가짜 제약(습관적 자기중단)**: 8개씩 검색해서 성공률이 떨어지면("이번 배치 8개 중
  1개만 확정됐다") 별다른 지시 없이 스스로 "여기서 정리하는 게 낫겠다"고 판단해서 멈추는
  경향이 있었다. 이건 실제 기술적 한계가 아니라 임의로 세운 중단 기준이었다.
  **사용자가 계속하라고 했다면, 성공률이 낮아져도 실제 200회 한도에 닿기 전까지는
  스스로 멈추지 말고 계속 진행할 것.** 배치 성공률이 낮아지는 건 "그만할 신호"가 아니라
  "남은 인원이 마이너해졌다"는 신호일 뿐이다 — 계속할지 여부는 사용자가 정할 일이다.

**절대 금지**:
- Apify(유료 API)는 사용자에게 비용을 먼저 알리고 명시적 승인을 받기 전까지 실행 금지

  WebSearch로 더 시도하지 말고 Apify 승인 여부만 사용자에게 물어볼 것.
- 검색어에 클럽명·행사명 붙이기 금지(위에서 반복 강조한 이유 그대로).

**미해결로 남겨둔 것**: 클럽명 오파싱 재검증(2026-08-27) 중 `SPECIAL GUEST`,

from djs d

join club_lineups l on l.id = s.lineup_id
left join clubs c on c.id = l.club_id

## 왜 이게 다 안 채워져 있나

`club_events`/`club_lineups` 자동 수집(수·금 pg_cron)이 클럽 인스타 캡션에서 DJ·래퍼 이름을 뽑아 `djs`/`artists` 마스터를 만든다. 이름은 자동으로 나오지만 **인스타 핸들까지 확신을 갖고 자동 채우는 건 극히 일부**다 — 아래 "확실"/"불확실" 구분 없이 대충 이어 붙이면 동명이인·팬계정으로 오연결된다(실제로 겪은 사고: `Ash` → 무관한 `@ash.island`로 잘못 저장됐던 적 있음, 되돌림).

## 검증된 방법 (효과순)

### 1. 구글 검색 — 사람이 직접 (가장 정확, 가장 빠름)

**`Claude Code 세션의 WebSearch 도구로 하지 말 것.`** 이 도구는 구글 SERP의 "AI 개요"와 지식 패널을 받지 못하고 링크 제목만 받는다. 그 결과 "ARKINS"를 검색하면 나무위키가 "대한민국의 DJ, 강남 클럽씬 1군"이라고 딱 짚어주는데도 WebSearch는 그 요약을 못 보고 팔로워 2,976명짜리 무관한 해외 계정을 상위로 착각한 사례가 반복됐다. 반면 브라우저로 직접 구글 검색하면 AI 개요가 "한국 활동 DJ(VICTA): 홍대 등에서 레지던트로 활동하는 @victa_dj"처럼 동명이인까지 갈라준다.

**검색어 공식**: `{이름} DJ` 또는 `{이름} 래퍼`. 클럽명을 붙이면 오히려 클럽 계정이 상위로 밀고 올라와 방해가 된다(실측).

`/admin/performers`의 "구글" 링크가 이미 이 공식으로 걸려 있다.

#### 검색 실전 팁 (WebSearch로 헛돌지 않으려면)

**시작 전에 이름부터 걸러라.** 검색해봐야 소용없는 이름이 섞여 있다. 아래는 검색 대상이 아니다:
- **클럽명 = DJ명 형태**: `BERMUDA DJ`, `MUFFIN`, `RESIDENTS`, `Who's Next?` — 사람이 아니라
  "○○ 클럽의 DJ들" 통칭이거나 이벤트 제목 오파싱이다. 검색하면 클럽 공식 계정만 반복해서
  나온다. 개인 계정이 존재하지 않으므로 **건너뛰고 정리 대상으로 분류**한다.
- 판별법: 이름이 클럽 이름과 같거나, 복수형(RESIDENTS/GUESTS/LINEUP)이거나, 물음표·느낌표가
  붙어 있으면 사람 이름이 아닐 확률이 높다.

**짧은 영단어 이름은 WebSearch로 못 찾는다.** `SMASHER`, `YUUKI`, `IMPACT`, `RABI`, `VIS` 같은
이름은 전 세계에 동명 계정이 수백 개라 링크 제목만 보는 WebSearch로는 원천적으로 판별 불가다.
검색 결과에 나이지리아·케냐·스페인 DJ가 나온다면 **틀린 게 아니라 방법이 안 맞는 것**이다.
이런 이름은 아래 2·3번(팔로잉 네트워크)으로만 풀린다 — 시간 낭비하지 말고 넘겨라.

**WebSearch로 성공 가능한 조건** (셋 다 충족할 때만 시도):
1. 이름이 고유하다 (한글 이름, 또는 `ZESTURE`·`ARKINS`처럼 사전에 없는 조어)
2. 검색 결과 **첫 페이지 안에** 나무위키·멜론·바이브·힙합엘이 등 **한국 음악 매체**가 있다
3. 그 페이지 제목·스니펫에 "DJ" 또는 "래퍼"와 **한국 지명/클럽/레이블**이 같이 보인다

셋 중 하나라도 빠지면 저장하지 말고 미확보로 남긴다. **미입력이 오연결보다 낫다** — 실제로
`Ash` → `@ash.island`(무관한 인물)로 잘못 저장한 뒤 되돌린 사고가 있었다.

**검색어 변형 순서** (앞의 게 실패했을 때만 다음으로):
1. `{이름} DJ` — 기본
2. `{이름} 디제이` — 한글 표기 매체가 잡힌다
3. `"{이름}" 홍대 OR 강남 클럽` — 따옴표로 정확 일치 강제
4. `site:instagram.com {이름} dj korea` — 인스타 도메인 한정

3·4번까지 갔는데도 한국 매체가 안 걸리면 그 이름은 검색으로 안 나오는 이름이다. 포기가 정답이다.

**보고 형식**: 못 찾은 건 이유를 붙여서 넘겨라 — `이름 / 판정(비인물·동명이인과다·검색불가) / 근거 1줄`.
그래야 다음 사람이 같은 이름을 또 검색하지 않는다.

### 2. 클럽 인스타 "팔로잉 목록" 조회 — API, 대량 처리 가능

클럽 계정은 팔로잉이 20~60개로 매우 적고, 그 안에 레지던트 DJ가 들어있다. 예: `@bermuda_hongdae` 팔로잉 20개 중 VICTA·SWEED·MINUTE·BRIXX·ZESTURE·NEWT·ARKINS 발견.

```
Apify actor: dead00~instagram-followers-following-scraper-no-cookies
input: { usernames: [클럽핸들...], dataToScrape: "Followings", maxResultsPerUser: 80~150 }
```

받은 `fullName`/`username`을 DJ 표기와 **정확 일치**로만 매칭한다(부분 일치 금지 — 오연결 원인). 특히 바이오에 `"DJ " + 이름`이 그대로 있으면 확정으로 취급해도 된다(예: "DJ ZESTURE / CLUB BERMUDA MANAGER").

이미 만들어둔 스크립트: `scripts/discover-dj-instagram.mjs` — 팔로잉 수집 → 프로필 상세 조회 → strong(자동 저장)/weak(사람 확인용 출력) 분류까지 자동.

### 3. 확보된 계정끼리 "팔로잉 네트워크" — 같은 클럽 소속끼리만 통함

DJ/아티스트는 서로 팔로우하지만 **무작위가 아니라 같은 클럽·같은 씬끼리** 뭉친다. 실측: 버뮤다 DJ 5명의 팔로잉 750개에서는 미확보 인원이 0건 걸렸는데, EGG 소속 FELIX 한 명의 팔로잉에서는 EGG 동료 MR.TMI(`@13reasonlive`, fullName "Mr TMI")가 바로 나왔다. 시드를 "아무 확보 인원"이 아니라 **"같은 클럽/같은 무대 소속 확보 인원"**으로 좁혀야 한다.

스크립트: `scripts/discover-via-network.mjs` (DJ, 클럽 단위) — 아티스트용은 "같은 이벤트에 함께 출연" 기준으로 같은 로직을 짜면 된다(스크립트 안 로직 참고).

### 4. 캡션 `@태그` 자동 추출 — 이미 자동 수집에 내장됨, 손댈 필요 없음

## 리소스 제약

- **Apify**: 이 프로젝트 계정은 무료 크레딧 $5/월. 이번 세션에서 팔로잉 스크래핑으로 소진했다(`monthlyUsageUsd: 5.01/5.00`). 초과 시 액터 호출 자체가 `Monthly usage hard limit exceeded`로 즉시 거부된다. 재개 시점은 `monthlyUsageCycle.endAt` 확인 (`Apify /users/me/limits` API). 유료 전환 없이는 다음 결제 주기까지 API 경로(2, 3번 방법) 사용 불가 — 그 기간엔 1번(구글 직접 검색)과 4번(자동 캡션)만 가능.

## 클럽명 오파싱 검증 (2026-08-26 발견 및 수정)

`djs` 테이블에 **클럽 이름이 그대로 DJ 이름으로 잘못 들어간 행**이 다수 발견됐다. 원인은
포스터 Vision 파싱 프롬프트(`src/lib/lineups/prompt.ts` / `supabase/functions/_shared/lineup-prompt.ts`)에
"타임테이블 슬롯에 클럽 이름/로고가 나오면 DJ로 넣지 마라"는 배제 규칙이 없었기 때문 — 클럽이
마지막 클로징 세트나 섹션 헤더에 자기 클럽명을 그대로 써넣는 경우, LLM이 그걸 그대로 `dj_name`에
담았다. **두 프롬프트 파일 모두 이 규칙을 추가해 수정 완료**(`node scripts/check-lineup-prompt-sync.mjs`로
동기화 확인됨) — 새로 수집되는 건은 이제 안 걸린다. 기존에 이미 들어간 오탐은 발견하는 대로 계속 정리 필요.

**확인·정리된 사례** (모두 `deleted_at` soft delete):
- `DX`, `TECHNO IN HANGANG`, `MUFFIN` — `clubs.name`과 정규화 후 정확 일치, 각각 라인업 마지막
  슬롯(클로징/브랜드 세트)에서 유입. `lineup_sets` 연결은 그대로 두고 `djs.deleted_at`만 세팅.
- `RESIDENTS`, `Who's Next?` — 사람 이름이 아니라 "레지던트 진" 통칭/이벤트 문구. 같은 클럽
  라인업에서 여러 날짜에 걸쳐 마지막 슬롯에만 반복 등장하는 패턴으로 판별.

**판별 방법** (의심 가는 이름이 있으면 이 순서로 확인):
1. `clubs.name`과 정규화(소문자, 특수문자 제거) 후 정확 일치하는지 확인
2. `lineup_sets` → `club_lineups` → `clubs`로 원본 라인업 전체를 펼쳐서, 같은 슬롯에 반복 등장하는
   패턴(특히 마지막 시간대에만 나옴)인지 확인 — 진짜 DJ는 여러 클럽·여러 날짜에 흩어져 나오고,
   오탐은 한 클럽의 클로징 슬롯에만 몰린다
3. 이름이 공백 포함 3단어 이상, 물음표/느낌표 포함, `RESIDENTS`/`GUEST`/`VARIOUS`/`TBA` 등 복수·통칭형이면 1차 의심

**분리 보류된 케이스**: `GOBI / SUNA` — 슬래시로 **두 사람이 한 행에 합쳐진** 오파싱(GOBI는 vurt.
신규 레지던트, SUNA는 기존 레지던트로 WebSearch에서 각각 확인됨). 클럽명 오탐이 아니라 병합
오탐이라 삭제 대상은 아니지만, `lineup_sets` 재배선이 필요한 편집이라 이번 세션에서는 손대지
않고 미입력 상태로 남겨뒀다. 다음에 손볼 때는 `GOBI`, `SUNA` 두 행을 새로 만들고 해당
`lineup_sets.dj_id`를 원본 포스터 대조해서 재배정할 것.

**판정 보류(불확실)**: `NO RETRUN BOY` — 오타("RETRUN")가 있어 팀/아티스트명일 가능성이 있고
다른 슬롯들과 동일한 패턴(1회 등장)이라 클럽명 오탐 근거는 약함. 사람이 아니라고 확신할 수
없어 삭제하지 않고 미입력으로 유지.
